kTranslationHelper

A dependency-free JavaScript plugin that lets visitors of a multi-language website flag and fix translations: correct a mistake in the language they're reading, or add a missing translation for any language you support.

Overview

kTranslationHelper is for sites that are already translated. Each translatable element carries its translation key in an attribute. When the helper is active, those elements are highlighted; the visitor holds Shift and clicks one, edits the text in a dialog, and the suggestion is sent to a URL (or function) you provide.

The plugin handles: highlighting, the trigger, the editor dialog, language selection, placeholder checks, submitting, and remembering state between pages. Your app handles:

  • Activation — a button, menu item or keyboard shortcut that calls helper.toggle(). Show it to the people you want suggesting translations, but treat that as convenience, not access control: anyone can turn the mode on from the browser console or by editing localStorage, so your backend must decide whose suggestions to accept.
  • Storage — the backend that receives suggestions and decides what to do with them (queue for review, apply directly, open a ticket …).
  • Rendering — your existing i18n layer. The helper never needs to know how you load translations; it can optionally ask for raw strings via getSource.

Quick start

1. Include the script

Use the classic build (adds window.kTranslationHelper) or the ES module. No build step or dependencies.

<script src="dist/ktranslationhelper.js"></script>
<!-- or -->
<script type="module">
  import kTranslationHelper from './dist/ktranslationhelper.mjs';
</script>

2. Mark up translatable text

Most i18n setups already output something like this. Use whichever attribute name you like.

<html lang="es">
…
<h1 data-i18n="home.title">Bienvenido</h1>
<input type="search" data-i18n-attr="placeholder:search.placeholder" placeholder="Buscar…">

3. Initialise and give users a way to turn it on

Call init() anywhere — in <head>, at the end of the page or from a module. Its interface is added to <body> as soon as that exists.

const helper = kTranslationHelper.init({
  keyAttribute: 'data-i18n',          // required
  defaultLanguage: 'en',              // required
  languages: ['en', 'es', 'de', { code: 'ar', name: 'العربية', dir: 'rtl' }],
  submitUrl: '/api/translation-suggestions',
});

document.querySelector('#suggest-translations')
  .addEventListener('click', () => helper.toggle());

That's it. Once a visitor turns it on, it stays on as they move between pages until they press Exit on the badge (or your app calls helper.deactivate()).

How it works

  1. The visitor turns on translation mode.your app
  2. Every translatable element is outlined, a badge appears in the corner, and a short instruction message is shown (once per session by default). Help on the badge explains the colours and the steps below, worded for your configuration.plugin
  3. The visitor holds Shift and clicks some text. Normal clicks still work, so links and buttons keep working while the mode is on. On touch screens, a long press does the same.plugin
  4. A dialog shows the current text, the original (source-language) text, and a Translate to list that remembers the last language chosen. If that differs from the page's language a clear notice says so, with a one-click switch back. The proposal is pre-filled with the current text.plugin
  5. On submit the suggestion is POSTed to submitUrl (or passed to your submit function), and the result message is shown. If the edit was in the page's language, the text on the page is updated straight away (updateInPlace). When the string was a missing translation and others remain, a Next missing button takes the translator to the next one.plugin
  6. Your backend stores or applies the suggestion.your app

The two everyday uses both follow this flow: correcting a mistake (leave the language as it is and edit), and adding a missing translation — for an existing language or one you're just starting (choose the language, then type).

Marking up translatable text

Attributes

OptionExample markupPurpose
keyAttributerequired<p data-i18n="cart.empty">The element's text is translatable, and this is its key.
attrMapAttribute<input data-i18n-attr="placeholder:form.email; title:form.email.tip">Translatable attributes — placeholders, tooltips, alt text, aria-label … Pairs of attribute:key separated by ;.

Attributes whose value is code are never editable, whatever the mapping says: event handlers (onclick …), style, srcdoc, formaction and is. URL attributes such as href and src are left out too unless you set allowUrlAttributes: true — most translators are not developers and shouldn't be asked to edit them — and even then a javascript:, data: or vbscript: value is not applied to the page. Your backend must still validate every attribute value it stores.

When an element has more than one string — a button with a label and a tooltip, or translatable text inside a translatable parent — the editor shows a Text to translate picker. Text that can't be clicked (<option>s, collapsed sections, the page <title>) is reachable from All text on the badge, which lists every string on the page and lets you filter.

Languages

The language of the clicked text is resolved in this order:

  1. the nearest element with langAttribute, if you set that option;
  2. the nearest standard lang attribute (usually <html lang>), unless useLangAttribute: false;
  3. defaultLanguage.

So a quote in <blockquote lang="es"> on an English page is correctly treated as Spanish. languages is the list offered in Translate to; leave it out and only the page's language can be edited (corrections only). Each entry is a code or an object:

languages: [
  'en',                                     // name from Intl.DisplayNames ("English"), dir detected
  { code: 'zh-Hans', name: '简体中文' },
  { code: 'ar', name: 'العربية', dir: 'rtl' }, // the text box switches to right-to-left
]

sourceLanguage (defaults to defaultLanguage) is the language your strings are written in; when getSource is set its text is shown as Original for reference.

HTML strings

By default everything is plain text: the plugin reads textContent and never inserts markup. Set allowHtml to let visitors edit markup:

allowHtml: true                                   // every string
allowHtml: (el, key) => el.hasAttribute('data-i18n-html')  // per element

For HTML strings the editor shows and edits innerHTML, and the payload has html: true.

Your backend must sanitise HTML suggestions. Anyone who can open the editor can submit anything. Allow a short list of tags and attributes and check link URLs — see docs/backend/lib.php for an example. Note that with the default updateInPlace: 'always' the visitor's raw HTML is written into their own page before your backend answers (it affects nobody else); return the sanitised text in the response and the plugin shows that instead, or use 'success'.

Raw strings (getSource)

What's on the page isn't always the string you store. "Hello {name}, you have {count} messages" is rendered as "Hello Ben, you have 3 messages"; if the editor used that, a translator would save "Ben" and "3" into the translation. Give the plugin a way to fetch the raw string and it uses it everywhere instead:

getSource: async (key, lang) => {
  // Return the stored string, or null if there is none (not translated yet).
  return myI18n.getRaw(key, lang) ?? null;
},

It's called for the page's language (the Current text), the sourceLanguage (the Original), and the chosen Translate to language (Existing translation). Results are cached per page; call helper.clearCache() if your translations reload. Without getSource the plugin falls back to the element's text and the Original and Existing fields aren't shown.

Submitting

Either give a URL, or a function. A function is useful for GraphQL, custom auth, queuing offline, or — as the demo does — a static host with no server at all:

// A static JSON file can't receive a POST, so GET it instead.
submit: async (payload) => {
  const res = await fetch('static-backend/response.json');
  return res.json();  // { "ok": false, "message": "The demo page does not have a backend …" }
},

Local mode (no backend)

Leave out both submitUrl and submit and nothing is sent: submitting applies the text to the page and shows "Applied to this page only. It will be lost when the page is reloaded." Useful for trying wording, for a static demo, or while the backend is still being written. onSubmit still fires, with result.local === true.

With a backend, updateInPlace: 'always' (the default) gives visitors the same instant feedback even when it answers ok: false; their change is only in their browser until it is reloaded.

Response

Reply with JSON:

{ "ok": true,  "message": "Thanks! A reviewer will look at it." }
{ "ok": true,  "message": "Saved.", "text": "Votre panier est <strong>vide</strong>" }
{ "ok": false, "message": "That language isn't open for suggestions yet." }

The request counts as successful when the HTTP status is 2xx and ok isn't false. If you changed the text before storing it (sanitised HTML, trimmed whitespace …), return it as text: the plugin then shows that on the page rather than what was typed. message is shown to the visitor (a default is used if it's missing), so write it in their language if you can — payload.pageLang tells you which. A submit function can return the same object, true/undefined (success), false (failure) or a string (a success message); throwing counts as failure.

Writing a backend

The backend is yours to write, and it should match how your translations are stored. Some guidance:

Queue suggestions for review rather than applying them directly. The editor can be opened by anyone who can turn translation mode on. Store suggestions with who made them and when, and let a trusted person accept them. Apply directly only for trusted, signed-in translators.

Checklist

  • Authenticate and authorise the request; use CSRF protection (the headers option can send your token).
  • Check lang against a list of allowed languages — never build a file path from it directly.
  • Only accept keys that exist in your source language.
  • Limit the text length and strip control characters.
  • Sanitise HTML for keys that allow it; treat every other key as plain text and render it with textContent or proper escaping.
  • Rate-limit per user or IP.
  • Return { ok, message } JSON with a sensible HTTP status, plus text if you altered the string.

Minimal example (PHP, review queue)

<?php
// POST /api/translation-suggestions — stores suggestions for review.
session_start();
header('Content-Type: application/json');

$in = json_decode(file_get_contents('php://input'), true) ?: [];
$languages = ['en', 'es', 'de', 'ar'];

// CSRF: only our own pages may post here (or check a token sent with the `headers` option).
if (strtolower($_SERVER['HTTP_SEC_FETCH_SITE'] ?? 'same-origin') !== 'same-origin') { http_response_code(403); exit(json_encode(['ok' => false, 'message' => 'Forbidden.'])); }
if (empty($_SESSION['user_id'])) { http_response_code(401); exit(json_encode(['ok' => false, 'message' => 'Please sign in.'])); }
if (!in_array($in['lang'] ?? '', $languages, true) || !is_string($in['key'] ?? null) || !is_string($in['text'] ?? null)
    || mb_strlen($in['text']) > 2000) {
    http_response_code(422); exit(json_encode(['ok' => false, 'message' => 'Invalid suggestion.']));
}

$pdo->prepare('INSERT INTO translation_suggestions (tkey, lang, text, original, page_url, comment, user_id, created_at)
               VALUES (?, ?, ?, ?, ?, ?, ?, NOW())')
    ->execute([$in['key'], $in['lang'], trim($in['text']), $in['original'] ?? null, $in['url'] ?? null,
               $in['comment'] ?? null, $_SESSION['user_id']]);

echo json_encode(['ok' => true, 'message' => 'Thanks! A reviewer will look at your suggestion.']);

The demo ships two backends you can read: docs/static-backend/ (always answers that nothing was saved) and docs/backend/ (PHP, writes straight into the JSON files, for local use only).

With the default updateInPlace: 'always', the page shows the new text as soon as it is submitted. If suggestions go to a review queue, you may prefer 'success' or false so visitors don't think the change is already live. The suggested mark (suggestedAttribute) tells them which strings they have already sent.

Activation & persistence

Turning the mode on is up to your app — you decide who sees the button:

button.addEventListener('click', () => helper.toggle());

// Optional keyboard shortcut
addEventListener('keydown', (e) => {
  if (e.altKey && e.code === 'KeyT') { e.preventDefault(); helper.toggle(); }
});

// Keep your button in sync, including when it's re-enabled on page load
kTranslationHelper.init({ …, onActivate: () => setPressed(true), onDeactivate: () => setPressed(false) });

While active, the state is saved (in localStorage by default), so the helper turns itself back on as the visitor moves around the site. They leave with Exit on the badge, your button, or helper.deactivate(). Use persist: 'cookie' if your server needs to know (for example to render extra attributes or skip caching), or persist: false to switch persistence off.

While active, <html> gets the class kth-active (plus kth-mod while the trigger keys are held, and kth-picking in pick mode), which you can use in your own CSS.

Touch screens

Touch screens have no Shift key, so there are two alternatives, both on by default:

  • Long press on highlighted text opens the editor (the system's text-selection menu is suppressed on highlighted text while active). Configure with longPress and longPressDelay.
  • Pick text on the badge: the next tap or click on translatable text opens the editor, then normal browsing resumes. Esc cancels. Your app can call helper.pick() too.

Keyboard

Visitors who don't use a mouse can press the hotkey (Shift + F2 by default) while a translatable element has focus — a link, a button, a form field with a translatable placeholder — to open the editor for it. With the mouse over some text and nothing translatable focused, the hotkey opens that text instead. The instruction message mentions it. Set hotkey: false to turn it off, or choose another combination such as 'mod+shift+e'.

Inside the editor, Ctrl/Cmd + Enter submits and Esc closes. Everything else — All text, the filters, Next missing — is an ordinary button.

Drafts & suggested marks

Closing the editor with an unsent edit keeps it as a draft for that string and language until the page is reloaded. Opening the same string again restores it, with a Discard link. There is no "are you sure?" dialog.

Once a suggestion has been sent (accepted by the backend, shown on the page by updateInPlace, or applied in local mode), the plugin sets suggestedAttribute on the elements that show it (a green outline), tags it suggested in All text, and says so at the top of the editor if it is opened again. This is remembered for the browser session (sessionStorage), so it survives moving between pages.

With missingAttribute set, the badge shows how many strings on the page are still fallbacks, All text has a Missing only filter, and after filling in a gap the editor stays open with a Next missing button that scrolls to and opens the next one. "Missing" means the page language's gaps; gaps in other languages need getSource and are not counted.

Interface text

The plugin's own interface is in English by default. Override any string with strings; ready-made translations are in dist/locales/ (es, zh-Hans, ar, plus en.json as a template for new ones):

const strings = await fetch(`/js/ktranslationhelper/locales/${lang}.json`).then((r) => r.json());
kTranslationHelper.init({ …, strings, uiLanguage: lang });

Strings can contain {placeholders}: {keys} in message and messageHotkey, {count} and {max} in the counters, {lang}, {target}, {page} and {list} elsewhere. Language names in {lang}, {target} and {page} are given in the page's language ("Alemán" on a Spanish page), and the Translate to list shows both that and the language's own name ("Alemán (Deutsch)"). kTranslationHelper.strings lists every key. New locale files are very welcome as contributions.

Theming

The badge and dialogs live in a Shadow DOM, so your site's CSS can't break them and theirs can't leak out. Adjust them with CSS custom properties on :root. Both light and dark defaults are built in; which one is used follows the theme option (by default the page's color-scheme, then the OS setting).

:root {
  /* Highlighting on the page */
  --kth-highlight: #cf6a00;       /* outline of translatable text */
  --kth-highlight-ring: rgba(207, 106, 0, .22);
  --kth-missing: #e11d48;         /* outline of text with missingAttribute */
  --kth-suggested: #16a34a;       /* outline of text already suggested this session */
  --kth-focus: #1d4ed8;           /* keyboard focus ring on highlighted text */
  --kth-focus-gap: #fff;

  /* Badge and dialogs */
  --kth-accent: #2563eb;  --kth-accent-text: #fff;
  --kth-bg: #fff;  --kth-text: #1f2328;  --kth-muted: #59636e;
  --kth-border: #d1d9e0;  --kth-soft: #f6f8fa;
  --kth-warn-bg: #fff8c5;  --kth-warn-text: #6b4f00;
  --kth-error: #cf222e;  --kth-success: #1a7f37;
  --kth-font: system-ui, sans-serif;
}

The defaults meet WCAG 2.1 AA: text at 4.5:1 and outlines at 3:1 on light and dark backgrounds. If you change them, keep those ratios. The three states also differ in outline style, not just colour: translatable text is dashed, missing text dotted and suggested text double, so they can be told apart without colour vision. Keyboard focus on highlighted text gets its own ring (--kth-focus) so it stays visible under the highlight.

The badge sits at the inline end of the viewport (bottom-right on left-to-right pages, bottom-left on right-to-left ones) and the dialogs follow the page's direction.

When a string is chosen from All text or with Next missing, the page scrolls to it and its outline pulses for a second (class kth-flash).

Highlighting uses outline, so it doesn't shift your layout, and CSS attribute selectors, so content added after page load is highlighted automatically and frameworks like React or Vue can re-render freely.

Content Security Policy

The plugin adds two <style> elements: one to <head> for the highlighting and one inside its Shadow DOM. A policy with style-src but no 'unsafe-inline' blocks both, and the plugin then shows no highlighting and an unstyled badge. Give it your nonce: the classic build picks it up from its own <script nonce="…"> tag automatically; the ES module (or a script loaded another way) needs nonce: '…' in the options. Nothing else needs an exception — the plugin uses no inline scripts, no eval and no inline style attributes.

Running the demo

The demo is a small bakery site with three pages — Home (eleven numbered examples), About and Contact — in English, Spanish, Simplified Chinese and Arabic (right-to-left), plus French with an empty file so you can try building a language from scratch. Two Spanish strings are deliberately missing. Translations are plain JSON files in docs/lang/.

Turn translation mode on and move between the pages: it stays on, the instruction message isn't repeated, and the editor keeps the language you last translated into. The About page shares its image's alt-text key with the home page, so fixing it on one page fixes both.

The demo lives in the repository's docs/ folder. Pick the backend in docs/config.js:

window.DEMO_CONFIG = {
  backend: 'static',   // 'static' — any static host; nothing is saved
                       // 'php'    — writes suggestions into docs/lang/*.json
  showKey: false,
};

Static (no backend)

Upload the docs/ folder to any static host (it is what GitHub Pages serves) and open it. Suggestions get the reply "The demo page does not have a backend, so updates are not saved."

PHP (full demo)

# PHP 8.1+ with the json and dom extensions (both usually built in)
cd ktranslationhelper
php -S localhost:8000 -t docs
# open http://localhost:8000/ — after setting backend: 'php'

Suggestions are written straight into the JSON files. Reset translations on the page (or php docs/backend/reset.php) restores them from docs/lang/original/.

Tests

npm install --no-save playwright axe-core
node tests/demo.test.mjs      # starts its own php -S, runs both backends, restores docs/lang/
node tests/a11y.test.mjs      # WCAG 2.1 AA audit of the demo and docs with axe-core

The PHP backend is for trying things out on your own machine. It only answers requests from localhost or private network addresses (a check that any reverse proxy defeats, since it sees the proxy's address) and from its own pages (Sec-Fetch-Site / Origin, so another website open in your browser can't write to the files), and must not be deployed on a public server.

Limits

  • Shadow roots and iframes. Highlighting is done with a page-level stylesheet and elements are found with querySelectorAll, so text inside a web component's shadow root or inside an <iframe> is neither highlighted nor listed. Initialise a separate helper inside the iframe if you need it there.
  • ICU plurals and selects. The default placeholderPattern matches {name}, {{name}}, %s and %1$s. A whole ICU argument such as {count, plural, one {# item} other {# items}} is not matched, so the editor won't notice when one is dropped. If your strings use ICU syntax, pass a pattern that fits them, e.g. /\{\s*\w+\s*(?:,[^{}]*(?:\{[^{}]*\}[^{}]*)*)?\}/g, or null to switch the check off.
  • Missing counts only know about the page language (via missingAttribute), not about gaps in other languages.

Browser support

Current versions of Chrome, Edge, Firefox and Safari (desktop and mobile). The plugin uses <dialog>, Shadow DOM, :is() and ES2020, and has no dependencies. TypeScript declarations ship in dist/ktranslationhelper.d.ts. Building dist/ from src/ needs Node 18+ (node build.mjs); using the plugin needs nothing.
